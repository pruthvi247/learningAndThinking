## 1.2 Exploring Penetration Testing Methodologies

There are, of course, a number of different types of penetration tests. Often they are combined in the overall scope of a penetration test; however, they can also be performed as individual tests as well.

**Network Infrastructure Tests**
Testing of the network infrastructure can mean a few things. For the purposes of this course, we say it is focused on evaluating the security posture of the actual network infrastructure and how it is able to help defend against attacks. This often includes the switches, routers, firewalls, and supporting resources, such as authentication, authorization, and accounting (AAA) servers and IPSs. A penetration test on wireless infrastructure may sometimes be included in the scope of a network infrastructure test. However, additional types of tests beyond a wired network assessment would be performed. For instance, a wireless security tester would attempt to break into a network via the wireless network either by bypassing security mechanisms or breaking the cryptographic methods used to secure the traffic. Testing the wireless infrastructure helps an organization to determine weaknesses in the wireless deployment as well as the exposure. It often includes a detailed heat map of the signal disbursement.

**Application-Based Tests**
This type of pen testing focuses on testing for security weaknesses in enterprise applications. These weaknesses can include but are not limited to misconfigurations, input validation issues, injection issues, and logic flaws. Because a web application is typically built on a web server with a back-end database, the testing scope normally includes the database as well. However, it focuses on gaining access to that supporting database through the web application compromise. A great resource that we mention a number of times in this book is the Open Web Application Security Project (OWASP).

**Penetration Testing in the cloud**
Cloud service providers (CSPs) such as Azure, Amazon Web Services (AWS), and Google Cloud Platform (GCP) have no choice but to take their security and compliance responsibilities very seriously. For instance, Amazon created the Shared Responsibility Model to describe the AWS customers’ responsibilities and Amazon’s responsibilities in detail (see [_https://aws.amazon.com/compliance/shared-responsibility-model_](https://aws.amazon.com/compliance/shared-responsibility-model)).  
  
The responsibility for cloud security depends on the type of cloud model (software as a service [SaaS], platform as a service [PaaS], or infrastructure as a service [IaaS]). For example, with IaaS, the customer (cloud consumer) is responsible for data, applications, runtime, middleware, virtual machines (VMs), containers, and operating systems in VMs. Regardless of the model used, cloud security is the responsibility of both the client and the cloud provider. These details need to be worked out before a cloud computing contract is signed. These contracts vary depending on the security requirements of the client. Considerations include disaster recovery, service-level agreements (SLAs), data integrity, and encryption. For example, is encryption provided end to end or just at the cloud provider? Also, who manages the encryption keys–the CSP or the client?  
  
Overall, you want to ensure that the CSP has the same layers of security (logical, physical, and administrative) in place that you would have for services you control. When performing penetration testing in the cloud, you must understand what you can do and what you cannot do. Most CSPs have detailed guidelines on how to perform security assessments and penetration testing in the cloud. Regardless, there are many potential threats when organizations move to a cloud model. For example, although your data is in the cloud, it must reside in a physical location somewhere. Your cloud provider should agree in writing to provide the level of security required for your customers. As an example, the following link includes the AWS Customer Support Policy for Penetration Testing: [_https://aws.amazon.com/security/penetration-testing_](https://aws.amazon.com/security/penetration-testing).

The following is a list of some of the most common penetration testing methodologies and other standards:

**MIRE ATTA&k**
The MITRE ATT&CK framework ([_https://attack.mitre.org_](https://attack.mitre.org/)) is an amazing resource for learning about an adversary’s tactics, techniques, and procedures (TTPs). Both offensive security professionals (penetration testers, red teamers, bug hunters, and so on) and incident responders and threat hunting teams use the MITRE ATT&CK framework today. The MITRE ATT&CK framework is a collection of different matrices of tactics, techniques, and subtechniques. These matrices–including the Enterprise ATT&CK Matrix, Network, Cloud, ICS, and Mobile–list the tactics and techniques that adversaries use while preparing for an attack, including gathering of information (open-source intelligence [OSINT], technical and people weakness identification, and more) as well as different exploitation and post-exploitation techniques. You will learn more about MITRE ATT&CK throughout this course.

**OWASP WSTG**
The OWASP Web Security Testing Guide (WSTG) is a comprehensive guide focused on web application testing. It is a compilation of many years of work by OWASP members. OWASP WSTG covers the high-level phases of web application security testing and digs deeper into the testing methods used. For instance, it goes as far as providing attack vectors for testing cross-site scripting (XSS), XML external entity (XXE) attacks, cross-site request forgery (CSRF), and SQL injection attacks; as well as how to prevent and mitigate these attacks. You will learn more about these attacks in Module 6, “Exploiting Application-Based Vulnerabilities.” From a web application security testing perspective, OWASP WSTG is the most detailed and comprehensive guide available. You can find the OWASP WSTG and related project information at [_https://owasp.org/www-project-web-security-testing-guide/_](https://owasp.org/www-project-web-security-testing-guide/).

**NIST**
Special Publication (SP) 800-115 is a document created by the National Institute of Standards and Technology (NIST), which is part of the U.S. Department of Commerce. NIST SP 800-115 provides organizations with guidelines on planning and conducting information security testing. It superseded the previous standard document, SP 800-42. SP 800-115 is considered an industry standard for penetration testing guidance and is called out in many other industry standards and documents. You can access NIST SP 800-115 at [_https://csrc.nist.gov/publications/detail/sp/800-115/final_](https://csrc.nist.gov/publications/detail/sp/800-115/final).

**OSSTMM**
The Open Source Security Testing Methodology Manual (OSSTMM), developed by Pete Herzog, has been around a long time. Distributed by the Institute for Security and Open Methodologies (ISECOM), the OSSTMM is a document that lays out repeatable and consistent security testing ([_https://www.isecom.org_](https://www.isecom.org/)). It is currently in version 3, and version 4 is in draft status. The OSSTMM has the following key sections:

- Operational Security Metrics
- Trust Analysis
- Work Flow
- Human Security Testing
- Physical Security Testing
- Wireless Security Testing
- Telecommunications Security Testing
- Data Networks Security Testing
- Compliance Regulations
- Reporting with the Security Test Audit Report (STAR)

**PTES**
The Penetration Testing Execution Standard (PTES) ([_http://www.pentest-standard.org_](http://www.pentest-standard.org/)) provides information about types of attacks and methods, and it provides information on the latest tools available to accomplish the testing methods outlined. PTES involves seven distinct phases:

1. Pre-engagement interactions
2. Intelligence gathering
3. Threat modeling
4. Vulnerability analysis
5. Exploitation
6. Post-exploitation
7. Reporting

**ISSAF**

The Information Systems Security Assessment Framework (ISSAF) is another penetration testing methodology similar to the others on this list with some additional phases. ISSAF covers the following phases:

- Information gathering
- Network mapping
- Vulnerability identification
- Penetration
- Gaining access and privilege escalation
- Enumerating further
- Compromising remote users/sites
- Maintaining access
- Covering the tracks

No single methodology is suitable for the requirements of every engagement; however it is important to ground your practice in standards and methodologies that have been developed by security organizations and recognized experts

The OSSTMM audit is an accurate measurement of security at an operational level. Version 3 encompasses tests across all channels: Human, Physical, Wireless, Telecommunications, and Data Networks. ### Chapter-1
_What You Need to Know_

• **Main Ideas:** Defines the core concepts of operational security (OpSec) based on **separation** (Security) and **controls** (Safety). Introduces the specialized terminology and metrics used throughout the manual.

• **Key Facts:**

    ◦ **Security** is the separation of an asset and a threat. **Safety** is the control of a threat or its effects.
    ◦ **OpSec** is reduced to elements that quantify the **Attack Surface**.
    ◦ **Porosity** refers to all interactive points (Visibility, Access, or Trust).

    ◦ The **rav** is a scale measurement of the Attack Surface, where 100 rav signifies **Perfect Security** (exact balance of security/controls with operations/limitations).

    ◦ There are **Ten Controls** (5 Class A/Interactive: Authentication, Indemnification, Resilience, Subjugation, Continuity; and 5 Class B/Process: Non-repudiation, Confidentiality, Privacy, Integrity, Alarm).

    ◦ **Limitations** are flaws that reduce protection effectiveness, categorized as Vulnerability, Weakness, Concern, Exposure, and Anomaly.

    ◦ **Actual Security** is the logarithmic representation of Controls, Limitations, and OpSec at a particular moment.

• **Connection to Narrative:** Provides the essential lexicon and mathematical framework (OpSec, Porosity, Controls, Limitations, rav) that dictates how all security testing, analysis, and reporting in subsequent chapters must be conducted and quantified.

### Chapter-3
_Security Analysis_
Main Ideas: Describes the skills and techniques needed to transform raw test data into actionable security intelligence, emphasizing logic and facts over speculation.
• Key Events/Facts:
    ◦ Security Analysis focuses on measuring the Attack Surface, never analyzing the threat itself (which is reserved for risk analysis).
    ◦ Critical Security Thinking requires using logic and facts, and identifying logical fallacies often used as security qualifiers (e.g., "There is no such thing as 100% secure").
    ◦ Analysis follows a Six Step Analysis Technique and requires constant validation of sources and measurement of trust.
	    1. Build your knowledge of the target from a variety of the most contemporary, factual resources while avoiding commercially biased and speculative information.
	    2. Determine the global level of experience for the type of target and the amount of information possibly known about it.
	    3. Determine any bias or ulterior motives in the information sources.Translate jargon from information sources to similar or known words for comparison because what may sound new or complicated may just be a trick to differentiate something common.
	    4. Be sure the test equipment has been properly calibrated and the test environment verified to assure the results are not contaminated by the test itself.
	    5. Assure that the translation state of tools or test processes has been removed as much as possible so that the results do not come from the indirect sources in a process or the pre-analysis from some tools.
    ◦ Analysts must actively avoid Pattern Matching (skipping steps based on expected outcomes) and relying on Intuition.
    ◦ Transparent Reporting is essential, requiring the Analyst to report not just findings, but also Unknowns, Untested Targets, False Positives, and Failed Security Processes.
• Connection to Narrative: Serves as the crucial intermediary step between testing (Chapter 2) and quantification (Chapter 4), guaranteeing that the derived metrics are accurate and based strictly on verified operational facts, thereby removing bias and addressing the methodology's theme of transparency.

### Chapter-5
_Trust Analysis_
Main Ideas: Defines trust as a rational decision that can be quantified, and introduces the Trust Properties and Trust Rules to analyze relationships within OpSec.
• Key Events/Facts:
    ◦ In OpSec, Trust is a contributor to Porosity (an internal interaction between targets).
    ◦ It warns against common, illogical uses of trust like Composability (accepting group trust) and Transitivity (chain of trust).
    ◦ The Ten Trust Properties (e.g., Size, Symmetry, Consistency, Value, Porosity) are objective elements used to create trust.
    ◦ These properties are converted into quantifiable Trust Rules specific to the target (e.g., an employee) to determine trustworthiness and identify where controls are needed.
    ◦ Trust analysis minimizes bias and helps management find deficiencies that impact protection measures by measuring operational trust against security policy.
• Connection to Narrative: Provides the specific analytical framework for evaluating the "Trust" element of Porosity (Chapter 1 and 4), particularly crucial for testing Human Security (Chapter 7), ensuring that trust decisions are based on facts rather than subjective "gut instincts"

**Chapter 14**
_What You Get_
• Main Ideas: Presents the overarching strategy derived from applying the OSSTMM methodology, known as the Möbius Defense.
• Key Events/Facts: The manual recognizes that the perimeter is an illusion, comparing defenses to a Möbius Strip (no inside or outside). The Möbius Defense relies on three steps:
    1. Improving Verification and Analysis: Verifying operations and classifying flaws by operational effect.
    2. Establishing Defense in Width: Applying a balanced variety of all ten operational controls to each interactive point, rather than concentrating any control type ("Defense in Depth").
    3. Implementing a Trust Strategy: Using factual trust metrics to compartmentalize authorization, ensuring trustworthy individuals have more control and separating untrustworthy elements.
• Connection to Narrative: This chapter culminates the philosophy of the OSSTMM, demonstrating how combining OpSec definitions, quantitative metrics, and trust analysis leads to a complete, balanced, and highly efficient defensive strategy that reduces reliance on reacting to flaws.

# Lab Q&A

When OSSTMM guidelines are correctly followed, six assured outcomes are: ==Operational Security Efficiency, Transparency, Measurement Accuracy, Security Assurance, Risk Reduction, and Compliance==. These outcomes are the result of the methodology's comprehensive and structured approach to testing security by focusing on measurable and repeatable results. 

- **Operational Security Efficiency:** Improves the effectiveness and efficiency of security operations. 
- **Transparency:** Provides a clear and open view of the testing process and its findings. 
- **Measurement Accuracy:** Ensures that test results are quantifiable and reliable, allowing for objective assessment. 
- **Security Assurance:** Gives confidence that security controls are functioning as intended and meeting security requirements. 
- **Risk Reduction:** Identifies and helps eliminate vulnerabilities, thereby lowering the overall security risk to the organization. 
- **Compliance:** Verifies that the organization's security posture meets relevant legal and regulatory standards.

When combining the [4-Point Process](https://www.google.com/search?sca_esv=f9a4d5dbb28ed665&rlz=1C5CHFA_en&q=4-Point+Process&sa=X&ved=2ahUKEwiP5JT7huCQAxXhT2wGHZvpH3oQxccNegQIExAB&mstk=AUtExfDRqLp_4HSeAfLwgmT9GBPzW9QjtdueNuJor6Jm8_q_su2gXNCUctuU1awcpI9oCs-uwqzGoRR7onr5zYyv5m1TdpivCTuhMAKzVf2L87-qmTsUKhEIcciiPVyWTURbCWc&csui=3) with the Trifecta within a [OSSTMM](https://www.google.com/search?sca_esv=f9a4d5dbb28ed665&rlz=1C5CHFA_en&q=OSSTMM&sa=X&ved=2ahUKEwiP5JT7huCQAxXhT2wGHZvpH3oQxccNegQIExAC&mstk=AUtExfDRqLp_4HSeAfLwgmT9GBPzW9QjtdueNuJor6Jm8_q_su2gXNCUctuU1awcpI9oCs-uwqzGoRR7onr5zYyv5m1TdpivCTuhMAKzVf2L87-qmTsUKhEIcciiPVyWTURbCWc&csui=3)-based approach, the ten steps are: ==1. Define Scope, 2. Assess Target, 3. Test Target, 4. Report Findings, 5. Perform Security Posture Evaluation, 6. Conduct Operational Security Measurement, 7. Perform Verification and Validation, 8. Conduct Threat and Vulnerability Analysis, 9. Perform Impact Analysis, and 10. Provide Recommendations for Improvement==. 

1. **Define the Scope:** Clearly establish the boundaries and objectives of the security test. 
2. **Assess the Target:** Gather information about the target system and its environment. 
- **Test the Target:** Conduct active and passive tests to identify vulnerabilities and security control weaknesses. 
- **Report Findings:** Document all findings, including the scope, methods, and results, in a structured report. 
- **Security Posture Evaluation:** Evaluate the overall security effectiveness and the strength of controls. 
- **Operational Security Measurement:** Measure the operational security using metrics and data from the testing phase. 
- **Verification and Validation:** Confirm that the vulnerabilities and security controls were assessed correctly and accurately. 
- **Threat and Vulnerability Analysis:** Analyze the identified vulnerabilities to understand potential threats and the likelihood of their exploitation. 
- **Impact Analysis:** Determine the potential business impact if a vulnerability were to be successfully exploited. 
- **Recommendations for Improvement:** Provide actionable recommendations to mitigate identified risks and improve overall security.
`What are the ten steps of applying the OSSTM when the 4 Point Process and Trifecta are combined?`
From the OSSTMM manual, page 45:  
1. Passively collect data of normal operations to comprehend the target.  
2. Actively test operations by agitating operations beyond the normal baseline.  
3. Analyze data received directly from the operations tested.  
4. Analyze indirect data from resources and operators (i.e. workers, programs).  
5. Correlate and reconcile intelligence from direct (step 3) and indirect (step 4) data test results to determine operational security processes.  
6. Determine and reconcile errors.  
7. Derive metrics from both normal and agitated operations.  
8. Correlate and reconcile intelligence between normal and agitated (steps 1 and 2) operations to determine the optimal level of protection and control which would best be implemented.  
9. Map the optimal state of operations (step 8) to processes (step 5).  
10. Create a gap analysis to determine what enhancements are needed for processes governing necessary protection and controls (step 5) to achieve the optimal operational state (step 8) from the current one.

`What is the stated purpose of the PTES? (**Hint**: Look in the FAQs)`
The stated purpose of the PTES (Penetration Testing Execution Standard), as found in its FAQs and documentation, is ==**to provide both businesses and security service providers with a common language and scope for performing and understanding security evaluations**==. 

More specifically, PTES aims to:

- **Standardize the penetration testing process** to ensure consistency, rigor, and transparency in security audits.
- **Help organizations understand what to expect from a penetration test** and the value it provides, linking technical findings back to business risks and impact.
- **Offer comprehensive, detailed guidelines** that cover the entire penetration testing lifecycle (from planning to reporting), serving as a technical baseline for security professionals. 

The ultimate goal is to improve the overall quality and effectiveness of penetration testing, enabling organizations to better protect themselves against cyber threats and meet regulatory compliance requirements.

`What are the five phases of the Web Security Testing Framework?`
The five phases of the Web Security Testing Framework ([OWASP WSTG](https://www.google.com/search?q=OWASP+WSTG&rlz=1C5CHFA_en&oq=What+are+the+five+phases+of+the+Web+Security+Testing+Framework%3F&gs_lcrp=EgZjaHJvbWUyBggAEEUYQNIBCDI0MzVqMGo0qAIAsAIB&sourceid=chrome&ie=UTF-8&mstk=AUtExfBaKZHeHHiFI-9wAyPgkk_kikE54MMmG4cbiG3vgRFkAMdGkK2oDfwShUud2RPF3tPr-Kpn9cBEkwqpCQIEGdZGTuINmC8MFPAd__MRbds4L9nzGB6EtsbfdyBHNcUKWEQ&csui=3&ved=2ahUKEwiOur_PiOCQAxX5WXADHXg3O6kQgK4QegQIARAB)) are integrated into the Software Development Life Cycle (SDLC) and occur at different stages: ==Phase 1 (Before Development Begins), Phase 2 (During Definition and Design), Phase 3 (During Development), Phase 4 (During Deployment), and Phase 5 (During Maintenance and Operations)==. This approach ensures that security is considered from the start rather than being an afterthought. 

The five phases of the Web Security Testing Framework

- **Phase 1: Before Development Begins:** This initial phase involves activities like creating a security requirements document and performing threat modeling to identify potential risks before any code is written.
- **Phase 2: During Definition and Design:** Testing in this phase focuses on the application's architecture and design, ensuring security controls are built in from the ground up.
- **Phase 3: During Development:** This phase involves performing security-focused activities on the code itself, such as secure code reviews and security testing of individual components.
- **Phase 4: During Deployment:** Once the application is ready to be deployed, security testing focuses on the configuration of the server and network environment to prevent vulnerabilities in the production environment.
- **Phase 5: During Maintenance and Operations:** In this ongoing phase, security testing continues to identify new vulnerabilities and ensure the application remains secure throughout its operational life, including during updates and patches.
`What is the stated purpose of the OWASP WSTG?`
The stated purpose of the OWASP Web Security Testing Guide (WSTG) is ==to provide a standardized, comprehensive methodology and framework for testing the security of web applications and services==. It is a resource for cybersecurity professionals and organizations to ensure consistent, repeatable, and rigorous security testing by focusing on real-world exploitation scenarios throughout the development lifecycle. 

- **Standardized Methodology**: WSTG provides a consistent and rigorous framework for testing, with a focus on well-defined testing categories and over 60 test cases.
- **Comprehensive Coverage**: It is designed to test all areas of a web application, from user input and authentication to cryptographic controls.
- **Real-World Focus**: The guide is centered on real-world exploitation scenarios, reflecting the practical perspective of an attacker.
- **Lifecycle Integration**: It helps integrate security testing into all phases of the software development lifecycle (SDLC), from conception and design to deployment and maintenance, rather than treating it as an afterthought.
- **Quality Control**: By providing a standardized approach, the WSTG helps ensure that testing is conducted under quality control and produces reliable, repeatable results.
`What are the twelve categories of active tests defined in the OWASP Web Testing Framework?`
The OWASP Web Security Testing Guide (WSTG) defines twelve categories of active tests within its framework for web application security testing. These categories are:

- **Information Gathering:** Collecting information about the target application and its environment.
- **Configuration and Deployment Management Testing:** Assessing the security of the application's configuration and deployment.
- **Identity Management Testing:** Evaluating the security of user identities and their management within the application.
- **Authentication Testing:** Testing the strength and resilience of the application's authentication mechanisms.
- **Authorization Testing:** Verifying that users have appropriate access levels and cannot bypass authorization controls.
- **Session Management Testing:** Examining the security of user sessions and their handling.
- **Input Validation Testing:** Identifying vulnerabilities related to improper handling of user input.
- **Error Handling:** Assessing how the application handles errors and prevents information leakage.
- **Cryptography:** Reviewing the implementation and effectiveness of cryptographic controls.
- **Business Logic Testing:** Testing for flaws in the application's business logic that could be exploited.
- **Client-side Testing:** Analyzing vulnerabilities present in client-side components and interactions.
- **API Testing:** Evaluating the security of application programming interfaces (APIs).

`Why did MITRE develop ATT&CK? (**Hint**: Look in the FAQs)`
MITRE developed ATT&CK ==to document common adversary tactics, techniques, and procedures (TTPs) based on real-world observations to create a common language for cybersecurity professionals==. The goal was to provide a knowledge base to help organizations better understand, detect, and respond to cyber threats by analyzing attacker behavior, improving defenses, and increasing security posture visibility. 

- **Document adversary behavior**: The primary purpose is to create a structured knowledge base of how adversaries operate during cyberattacks across different phases.
- **Provide a common language**: It established a standardized taxonomy to help security teams communicate more effectively about threats and to compare the effectiveness of different security controls.
- **Improve threat detection and response**: By understanding attacker tactics, organizations can use ATT&CK to enhance their threat intelligence, refine security strategies, and strengthen their incident response capabilities.
- **Identify security gaps**: The framework helps organizations identify vulnerabilities in their security architecture and prioritize which to remedy by allowing them to see their defenses from an attacker's perspective.
- **Aid in security skills training**: It serves as a valuable tool for new security staff, providing them with the collective knowledge to quickly get up to speed on threats.
